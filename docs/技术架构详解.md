# Xianyu RAG Agent 技术架构详解

> 本文档面向技术评审与面试，深入讲解系统的设计思路、核心模块实现原理、关键技术选型与权衡取舍。

---

## 一、项目背景与动机

### 1.1 要解决什么问题

闲鱼（Goofish）是阿里旗下的二手交易平台，卖家需要实时回复买家咨询。个人卖家难以 7×24 在线，市面上的自动回复工具存在三个核心短板：

| 痛点 | 表现 | 本系统的解法 |
|------|------|-------------|
| **知识不可控** | LLM 凭「模型自身知识」回复，不了解卖家自家商品的细节（成色、配件、保修条款） | RAG 知识库：卖家上传文档，技术专家回复时检索注入 |
| **回复无溯源** | 不知道 AI 回了什么、回了谁、基于什么知识 | 可视化平台：会话浏览 + 意图标签 + 检索结果标记 |
| **运维纯靠日志** | 改提示词要改文件重启、看数据要翻日志、知识库无管理界面 | 全栈可视化平台：在线编辑热更新 + 仪表盘 + 知识库 CRUD |

### 1.2 设计原则

- **轻量优先**：单机部署、SQLite + ChromaDB 文件存储，不引入 Redis/ES 等中间件
- **不阻断主流程**：RAG、LLM、可视化任一组件异常，机器人仍能正常回复
- **最小侵入扩展**：RAG 和 Web 平台作为独立模块叠加，不重构原有 Agent 逻辑

## 二、整体架构

### 2.1 双进程架构

系统采用 **bot 主进程 + web 进程** 的双进程设计，通过共享文件系统（SQLite + ChromaDB）交换数据，而非进程间 RPC：

```
┌─ Bot 进程 (asyncio 事件循环) ──────────────────┐
│  • WebSocket 长连接收发闲鱼消息                 │
│  • 消息解密 / 时效过滤 / 人工接管判断           │
│  • IntentRouter 意图路由                       │
│  • 专家 Agent 生成回复（TechAgent 调用 RAG）    │
│  • 控制队列轮询任务（执行 Web 下发的命令）       │
└──────────┬───────────────────────────┬─────────┘
           │                           │
     SQLite (data/chat.db)      ChromaDB (data/chroma/)
           │                           │
┌──────────▼───────────────────────────▼─────────┐
│  Web 进程 (FastAPI + Uvicorn)                  │
│  • REST API（仪表盘/会话/知识库/提示词）          │
│  • 静态文件托管（Vue3 SPA）                     │
│  • 读写同一份 SQLite + ChromaDB                │
└───────────────────────────────────────────────┘
```

**为什么选双进程而非单进程合并？**

- bot 进程跑在 asyncio 事件循环里，WebSocket 长连接 + 心跳 + Token 刷新都是常驻任务，FastAPI 若共享事件循环会与消息处理互相阻塞
- 双进程可独立重启：改了前端不需要断开闲鱼 WebSocket
- 部署灵活：不需要可视化平台的用户可以只跑 bot 进程

### 2.2 技术栈选型理由

| 组件 | 选型 | 为什么不选替代方案 |
|------|------|---------------------|
| 向量库 | ChromaDB | 纯 Python、文件持久化、自带元数据过滤。FAISS 更轻但元数据管理弱，Milvus/Qdrant 需要额外容器 |
| Embedding | DashScope text-embedding-v3 | 与 LLM 同供应商同 API_KEY，零额外配置。换 OpenAI/Cohere 只需改环境变量 |
| 后端 | FastAPI | 原生 async、与 bot 同为 Python 生态、可复用 context_manager。Flask 同步模型不适合 |
| 前端 | Vue3 + Element Plus | 组件库成熟、适合管理后台。用 ESM CDN 引入实现零构建，部署只复制 HTML/JS |
| 存储 | SQLite | 与原项目一致、单文件零运维。会话量级（日均百级）远未到需要 PostgreSQL 的程度 |
| 进程通信 | SQLite 命令队列 | 零新中间件、断线不丢命令。Redis Pub/Sub 会引入新依赖，与轻量原则不符 |

## 三、核心模块实现

### 3.1 多专家 Agent 路由

#### 设计思路

单一 LLM 难以同时兼顾「议价谈判」「技术解答」「日常客服」三种截然不同的对话风格。系统采用 **意图识别 → 专家分发** 的路由模式：

```
用户消息
   │
   ▼
IntentRouter.detect()
   │
   ├─ 1. 技术类关键词匹配？(参数/规格/型号/连接/对比)
   │     └─ 是 → TechAgent
   │
   ├─ 2. 价格类关键词匹配？(便宜/价/砍价/少点/\d+元)
   │     └─ 是 → PriceAgent
   │
   └─ 3. 都不匹配 → ClassifyAgent (LLM 兜底分类)
         └─ 返回 price/tech/default/no_reply
```

#### 三级路由策略（技术优先）

```python
class IntentRouter:
    def detect(self, user_msg, item_desc, context):
        # 1. 技术类关键词优先（正则 + 关键词）
        # 2. 价格类关键词其次
        # 3. 都不命中才调用 LLM 分类（省 Token）
```

**为什么不直接用 LLM 分类所有消息？**

- 关键词规则零延迟、零成本，能覆盖 70%+ 的明确意图
- 只有模糊消息才走 LLM 兜底，大幅降低 API 调用量和延迟
- 技术类优先于价格类：避免「这个多少钱能便宜点」被误判为纯议价而漏掉技术上下文

#### 各 Agent 的差异化设计

| Agent | 温度策略 | 特殊处理 |
|-------|---------|---------|
| PriceAgent | 动态：`min(0.3 + 议价轮次×0.15, 0.9)` | 议价轮次越多温度越高，回复越灵活 |
| TechAgent | 固定 0.4 | 注入 RAG 检索结果 + 启用联网搜索 |
| DefaultAgent | 固定 0.7 | 限制回复长度，短句风格 |
| ClassifyAgent | — | 只返回意图标签，不生成对话内容 |

动态温度策略的意义：首次议价时回复严谨（低温），多次拉锯后回复更灵活（高温），模拟真人谈判的节奏变化。

### 3.2 RAG 检索增强生成管线

这是本项目新增的核心模块，完整链路如下：

```
                    ┌─────────────────────────────┐
                    │      知识入库 (ingest)       │
                    │                             │
  原始文档 ───────► │ chunker 切分                │ ──► ChromaDB 向量入库
  (txt/md)         │ (段落优先+滑动窗口)          │     + SQLite 元数据登记
                    │      ↓                     │
                    │ DashScope embedding 批量化  │
                    └─────────────────────────────┘

                    ┌─────────────────────────────┐
                    │      检索注入 (search)       │
                    │                             │
  用户问题 ───────► │ query → DashScope embedding │
                    │      ↓                     │
                    │ ChromaDB cosine 检索        │ ──► 拼成知识文本块
                    │      ↓                     │      ↓
                    │ 元数据过滤(scope/item_id)   │ 注入 TechAgent system prompt
                    │      ↓                     │      ↓
                    │ 距离阈值过滤(≤0.6)         │ LLM 带知识上下文生成回复
                    └─────────────────────────────┘
```

#### 3.2.1 文档切分策略 (`chunker.py`)

```python
def chunk_text(text, chunk_size=400, overlap=50):
    # 1. 先按段落（换行）切，保持语义完整
    # 2. 段落超过 chunk_size 的，用滑动窗口二次切分
    # 3. 相邻块重叠 overlap 字符，保证跨块语义连贯
```

**为什么 chunk_size=400？** 闲鱼咨询是短文本场景，知识块不宜过长——过长会稀释向量相似度的区分度，且注入 prompt 后占用 token 预算。400 字约对应一段完整的产品说明或 FAQ 条目。

#### 3.2.2 向量存储与检索 (`store.py`)

ChromaDB 封装的关键设计——**预计算 embedding 直传**：

```python
class ChromaStore:
    def add(self, texts, embeddings, metadatas, ids):
        # embedding 由上层 RAGRetriever 预计算后传入
        # store 不绑定任何 embedding 模型
        self._collection.upsert(ids=ids, embeddings=embeddings, ...)
```

**为什么不直接用 ChromaDB 的内置 embedding function？**

- 解耦：换 embedding 模型时只改 retriever，不动 store
- 控制：embedding 计算可分批、可重试、可缓存，由 retriever 统一管理
- 避坑：ChromaDB 内置 embedding 函数依赖 onnxruntime，在 Alpine/Docker 环境容易出兼容问题

#### 3.2.3 检索器 (`retriever.py`)

核心的 `search` 方法实现了 **混合范围检索 + 距离过滤**：

```python
def search(self, query, item_id=None, top_k=3):
    q_emb = self._embed([query])[0]

    # 元数据过滤：给定 item_id 时召回「通用 + 该商品专属」
    where = {"$or": [{"scope": "shop"}, {"item_id": item_id}]} if item_id else {"scope": "shop"}

    results = self.store.query(q_emb, where=where, n_results=top_k)

    # 距离过滤：cosine 距离 > 0.6 的弱相关结果丢弃
    filtered = [r for r in results if r["distance"] <= 0.6]

    return "\n".join(f"[{i}] {r['content']}" for i, r in enumerate(filtered, 1))
```

**两级元数据过滤的设计意图：**

| scope | item_id | 检索时行为 |
|-------|---------|-----------|
| shop | — | 所有会话都能召回（退换货政策等通用知识） |
| item | 具体商品ID | 只有该商品会话能召回（特定产品参数） |

这样，买家问「这个手机电池多大」时，TechAgent 既会召回通用的退换货政策（如果相关），也会召回该商品的专属参数表，但不召回其他商品的知识。

**距离阈值 0.6 的作用：** 防止知识库为空或无相关知识时，硬塞进不相关的内容误导 LLM。宁可不注入，也不注入噪声。

#### 3.2.4 Agent 注入点

RAG 只在 `TechAgent` 注入，不动其他 Agent——议价和客服场景不需要技术知识库，注入反而可能干扰回复：

```python
class TechAgent(BaseAgent):
    def __init__(self, client, system_prompt, safety_filter, rag=None):
        super().__init__(...)
        self.rag = rag

    def generate(self, user_msg, item_desc, context, bargain_count=0, item_id=None):
        messages = self._build_messages(user_msg, item_desc, context)

        if self.rag is not None:
            knowledge = self.rag.search(user_msg, item_id=item_id, top_k=3)
            if knowledge:
                messages[0]['content'] += "\n▲知识库参考：\n" + knowledge

        # ... 调用 LLM 生成
```

### 3.3 上下文管理 (`context_manager.py`)

#### 数据模型

SQLite 中维护五张表，覆盖完整的会话生命周期：

```
messages               # 对话消息（user/assistant，带 intent 标签）
├── id, user_id, item_id, role, content, timestamp, chat_id, intent
│
items                  # 商品信息缓存（避免重复调闲鱼 API）
├── item_id, data(JSON), price, description, last_updated
│
chat_bargain_counts    # 议价轮次（按会话）
├── chat_id, count, last_updated
│
rag_documents          # RAG 知识文档元数据
├── doc_id, title, scope, item_id, source, chunk_count, status, created_at
│
control_queue          # 进程间命令队列
├── id, command, payload, status, result, created_at, executed_at
```

每个会话只保留最近 100 条消息（可配置），超出自动清理最旧的：

```python
    # 插入新消息

```

这避免了长会话的上下文无限膨胀，也控制了 LLM 的 token 消耗。

**为什么用 ESM CDN 而非 Vite 构建？**

| 维度 | ESM CDN | Vite + npm build |
|------|---------|-------------------|
| 部署 | 复制 HTML/JS 即可 | 需要 Node 构建环境 + 构建产物 |
| Docker | 不需要 Node 阶段 | 需要多阶段构建（先 Node 再拷 dist） |
| 开发 | 改完刷新即生效 | 需 `npm run dev` 热更新 |
| 维护 | 依赖少、链路短 | 依赖锁、构建配置 |

对于单用户管理后台，CDN 方案在开发效率和部署简洁性上完胜，且 Vue3 + Element Plus 都是真实使用的框架。

### 3.5 进程间通信：SQLite 命令队列

这是连接两个进程的桥梁——Web 平台需要控制 bot 进程（热更新提示词），但不能直接调函数。

#### 通信流程

```
Web 进程                          Bot 进程
   │                                │
   │  1. 用户点「保存并热更新」       │
   │  2. 写 prompt 文件             │
   │  3. INSERT control_queue       │
   │     (command='reload_prompts')  │
   │     (status='pending')          │
   │                                │
   │           (SQLite 文件)         │
   │                                │
   │                    4. 每 10s 轮询 fetch_pending_controls()
   │                    5. 执行 bot.reload_prompts()
   │                    6. UPDATE control_queue SET status='done'
   │                                │
   │  7. Web 轮询命令状态             │
   │     (或下次写命令时读上次结果)    │
```

**为什么不用 Redis Pub/Sub 或 HTTP 内部接口？**

- Redis：引入新中间件，违背轻量原则；且断线会丢消息
- HTTP 接口：bot 进程要额外开 HTTP 服务端口，增加复杂度
- SQLite 命令队列：**零新依赖、断线不丢命令（持久化）、与现有架构一致**

命令队列的幂等性设计：每条命令有唯一 id，执行后标记 `done`，重复轮询不会重复执行。

### 3.6 优雅降级机制

系统在任何组件异常时都不应崩溃，而是降级运行：

```python
# XianyuReplyBot._init_rag()
def _init_rag(self):
    try:
        self.rag = RAGRetriever(...)
    except Exception as e:
        logger.warning(f"RAG 初始化失败，将降级运行: {e}")
        self.rag = None  # None → TechAgent 跳过 RAG 注入

# TechAgent.generate()
if self.rag is not None:       # RAG 不存在则跳过
    try:
        knowledge = self.rag.search(...)
    except Exception as e:     # 检索失败也跳过，不影响回复
        logger.warning(f"RAG 检索异常: {e}")
```

降级链路：RAG 不可用 → TechAgent 不注入知识 → 仍用 LLM + 联网搜索回复 → 用户无感知。

## 四、关键数据流走读

### 4.1 一条买家消息的完整生命周期

```
1. 闲鱼 IM 推送 WebSocket 消息
   ↓
2. main.py handle_message()
   → ACK 确认
   → 解密消息（闲鱼消息是加密的）
   → 时效过滤（丢弃 5 分钟前的过期消息）
   → 提取 send_user_id / item_id / chat_id / send_message
   ↓
3. 判断消息类型
   → 自己发的消息？检查是否为人工接管切换命令
   → 人工接管模式中？只记录不回复
   → 系统消息（带中括号）？跳过
   ↓
4. 获取商品信息
   → 先查 SQLite items 表
   → 没有则调闲鱼 API 获取并缓存
   → build_item_description() 构建商品描述
   ↓
5. 获取对话上下文
   → context_manager.get_context_by_chat(chat_id)
   → 返回最近 N 条消息 + 议价次数
   ↓
6. bot.generate_reply(user_msg, item_desc, context, item_id)
   → IntentRouter.detect() 路由意图
   → 分发到对应 Agent
   → PriceAgent: 动态温度 + 议价策略
   → TechAgent: RAG 检索(item_id) → 注入 prompt → LLM
   → DefaultAgent: 日常回复
   → _safe_filter() 安全过滤（屏蔽微信号等）
   ↓
7. 后处理
   → 意图为 price？increment_bargain_count_by_chat()
   → 保存用户消息到上下文 (role=user)
   → 保存 Bot 回复到上下文 (role=assistant, intent=xxx)
   ↓
8. send_msg() WebSocket 发送回复
```

### 4.2 提示词热更新流程

```
1. 用户在 Web 平台编辑 tech_prompt → 点保存
2. PUT /api/prompts/tech → 写文件 prompts/tech_prompt.txt
3. INSERT control_queue (command='reload_prompts', status='pending')
4. 返回 { control_id: 1, message: "已写入命令队列" }
5. Bot 进程 control_loop() 每 10s 轮询
6. fetch_pending_controls() → 取到 reload_prompts
7. _execute_control() → bot.reload_prompts()
   → _init_system_prompts() 重新加载文件
   → _init_agents() 重建 Agent 实例（注入新 prompt + RAG）
8. ack_control(id, 'done') → 命令标记完成
9. 下条买家消息 → 新 Agent 生效，无需重启进程
```

## 五、技术亮点总结（面试重点）

### 5.1 RAG 管线的工程化细节

| 问题 | 解法 |
|------|------|
| Embedding API 有条数限制 | `_embed_batch_size=25` 自动分批，避免超限 |
| 弱相关结果污染回复 | cosine 距离 > 0.6 丢弃，宁缺毋滥 |
| 商品间知识串扰 | 元数据 `$or` 过滤：通用 + 该商品专属，不跨商品 |
| 向量库与元数据不一致 | 双写：Chroma 存向量 + SQLite 存文档元数据，删除时同步 |
| 文档切分破坏语义 | 段落优先切分，仅超长段落才滑动窗口，重叠 50 字保连贯 |

### 5.2 进程间通信的可靠性

- **持久化**：命令存 SQLite，进程崩溃重启后命令不丢
- **幂等**：命令有唯一 id + 状态机（pending→done/error），重复轮询不会重复执行
- **背压**：Web 端可批量写命令，Bot 端按 `LIMIT 5` 分批拉取，不会一次性卡死

### 5.3 前端零构建方案

用 importmap + ESM CDN 引入 Vue3 + Element Plus，省掉了 npm/webpack/vite 整条构建链：
- 开发：改 JS 刷新即生效
- 部署：Docker 不需要 Node 构建阶段，直接 COPY 静态文件
- 源码即产物：没有 `dist/` 中间层，维护链路短

### 5.4 动态温度策略

PriceAgent 的温度随议价轮次递增：`T = min(0.3 + count × 0.15, 0.9)`

这不是随意调参，而是模拟真人谈判节奏：
- 第 1 轮（T=0.3）：回复严谨、措辞克制
- 第 3 轮（T=0.75）：回复灵活、开始让步
- 第 4+ 轮（T=0.9）：接近随机，模拟「最后让一步」的松动感

### 5.5 意图标签全链路追踪

从意图识别到可视化展示的完整闭环：
```
IntentRouter 识别 → bot.last_intent → 存入 messages.intent 列 → dashboard 聚合统计 → 会话浏览展示标签
```
这让运营能看到「今天有多少咨询是议价、多少是技术问题」，而不只是看到消息条数。
